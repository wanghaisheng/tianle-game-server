# 天乐游戏服务器云原生化渐进迁移计划

## 一、迁移原则
- 渐进式：优先迁移低风险、低耦合、非核心数据。
- 可回滚：每一步都能回退到原有 Redis/MongoDB。
- 分层治理：将功能按缓存、会话、文件、结构化数据等分类迁移。
- 微服务化：逐步拆分业务逻辑，服务间通过 API 通信。

---

## 二、迁移分阶段实施

### 阶段1：评估与梳理
1. 数据梳理
   - 列出所有 Redis 用途（缓存、锁、排行榜、房间状态等）。
   - 列出所有 MongoDB 数据模型及其业务场景。
2. 代码抽象
   - 为 Redis/MongoDB 操作封装接口层，便于后续切换实现。

### 阶段2：优先迁移适合云 KV/对象存储的场景
#### 2.1 Cloudflare KV 替换 Redis（部分场景）
- 可迁移内容：用户会话、简单配置、临时缓存、非强一致性数据。
- 实施步骤：
  1. 封装 Redis/KV 统一接口（如 CacheService）。
  2. 新增 Cloudflare KV 实现，并灰度切流量。
  3. 数据双写，验证正确性后逐步切换。
  4. 保留原 Redis 作为兜底。

#### 2.2 Cloudflare R2 替换文件型数据
- 可迁移内容：用户头像、图片、日志、音视频等二进制大对象。
- 实施步骤：
  1. 梳理所有文件存储点，封装文件存储接口。
  2. 新增 R2 实现，迁移现有文件数据。
  3. 新增数据优先写入 R2，旧数据异步迁移。

### 阶段3：结构化数据分步迁移
#### 3.1 新功能/低频功能优先用 D1
- 适合迁移的内容：新上线的轻量级业务模块、管理后台、GM工具等。
- 实施步骤：
  1. 新业务直接用 D1 设计数据表。
  2. 旧业务拆分出低频、低耦合部分，重构为 D1 服务。
  3. 复杂业务继续用 MongoDB，逐步拆分。

#### 3.2 主业务数据长期保留 MongoDB
- 原因：D1 受限于容量、并发、SQL能力，难以承载高并发、复杂结构数据。
- 建议：核心业务（如房间、俱乐部、玩家主数据）继续用 MongoDB，待 Cloudflare D1 能力提升或业务拆分足够细再做迁移。

### 阶段4：微服务化与 API 化
- 拆分业务为独立服务（如房间服务、俱乐部服务、支付服务等），每个服务可独立选择最合适的数据存储（KV/D1/R2/MongoDB）。
- 服务间通过 HTTP/gRPC 通信，便于后续迁移和扩展。

---

## 三、迁移风险与应对
- 一致性风险：采用双写、数据校验、灰度切换，确保新旧数据一致。
- 性能风险：关键路径保留 Redis/MongoDB，逐步压测 KV/D1 性能。
- 功能缺失：对 KV/D1 不支持的功能（如事务、锁），保留原实现或寻找替代方案。

---

## 四、迁移里程碑示例
1. 完成 Redis/KV/R2 抽象层封装
2. 完成会话、配置缓存迁移到 KV
3. 完成图片/文件迁移到 R2
4. 新业务模块用 D1 实现
5. 逐步拆分并迁移低频业务到 D1
6. 业务服务 API 化，支持多后端并存

---

> 本计划为渐进式迁移建议，具体步骤可根据实际业务优先级和技术选型灵活调整。如需针对某一模块的详细迁移方案，请进一步指定。
